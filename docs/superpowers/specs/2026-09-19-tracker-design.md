# Дизайн: «Трекер чего угодно» — семейный трекер запасов и сроков годности

- **Дата:** 2026-09-19
- **Статус:** черновик на ревью
- **Рабочее название продукта:** «Трекер чего угодно» (репозиторий: `family-stock-tracker`)
- **Целевая платформа:** PWA (iPhone/iPad/Android/ПК), установка на домашний экран, полностью офлайн-работа

---

## 1. Резюме

Семейное PWA для учёта запасов (бакалея: консервы, крупы; аптечка: лекарства) с двумя видами отслеживания: **срок годности** и **количество** (ниже минимума → «пора купить», выше максимума → «избыток»). Приложение построено как локальная CRM-система дома с ролями «Администратор» и «Участник». Данные живут на устройстве (IndexedDB); совместное ведение одной семьёй в MVP обеспечивается безопасным обменом файлами-состояниями (экспорт/импорт со слиянием), а не затиранием. Слой серверной синхронизации предусмотрен архитектурно и будет добавлен вторым шагом.

## 3. Архитектура и стек

### 3.1. Стек

- **React 19 + TypeScript** — приложение
- **Vite 6 + vite-plugin-pwa** — сборка, service worker, офлайн-кэш, установка на домашний экран
- **Dexie 4 (IndexedDB)** — локальное хранилище, офлайн-источник истины
- **jspdf + jspdf-autotable** — PDF-отчёт трека
- **Vitest + Testing Library + fake-indexeddb** — тесты
- **GitHub Pages** (организация TestingInPractice), базовый путь `/family-stock-tracker/`

### 3.2. Принцип «локально-сначала, готово к синку»

Архитектура проектируется сразу под будущий серверный синк, чтобы файловый обмен (MVP) и серверная синхронизация (шаг 2) использовали **один и тот же механизм дельт и слияния**.

Каждая синхронизируемая запись несёт:
```
{ id, ..., updatedAt (мс), updatedBy (deviceId), deletedAt (null = жива, иначе могилка) }
```

- Слияние на уровне записи: «кто обновил позже — тот прав» (LWW по `updatedAt`).
- Удаления не стирают запись, а помечают могилкой `deletedAt`.
- В MVP слияние двухстороннее, но с эвристикой конфликта: файл несёт `exportedAt`; при импорте для каждой существующей локальной записи, изменённой **позже** `exportedAt` и **отличающейся** от пришедшей, фиксируется конфликт. Победитель — запись с более новым `updatedAt` (обычно локальная), обе версии сохраняются в журнале. С сервером это станет честным three-way merge.
- Журнал операций (append-only) объединяется по `deviceSeq` — дубликаты отбрасываются без потерь.

### 3.3. Таблицы Dexie

| Таблица | Содержимое |
|---|---|
| `household` | Один дом: название, id дома, подпись устройства, настройки (окно предупреждения N дней) |
| `deviceProfile` | «Кто я на этом устройстве»: роль (admin/member), хэш PIN (scrypt/argon2 через WebCrypto), deviceId, deviceLabel |
| `tracks` | Треки: бакалея, аптечка… |
| `categories` | Подкатегории внутри треков: аптечка дома, аптечка в машине, полка с крупами |
| `items` | Позиции с количеством, порогами, сроком, режимами отслеживания |
| `trackingMethods` | Способы отслеживания (создаёт админ): «Срок годности», «Остаток ниже минимума», «Остаток min+max» |
| `ops` | Журнал операций: тип, delta, автор, примечание, `deviceSeq` |

## 4. Модель данных

### 4.1. Иерархия и роли

```
ДОМ (семья)
 ├─ УСТРОЙСТВО: АДМИНИСТРАТОР / УЧАСТНИК        (+ PIN у админа)
 ├─ СПОСОБ ОТСЛЕЖИВАНИЯ (создаёт админ)
 │    «Срок годности» · «Остаток < min» · «Остаток min+max»
 ├─ ТРЕК (создают все)
 │    └─ ПОДКАТЕГОРИЯ (создают все)
 │         └─ ПОЗИЦИЯ
 │              количество · единица · min/max пороги · срок · режимы
```

- **Треки и подкатегории создают и админ, и участник.**
- **Способы отслеживания создаёт только админ** (экран настроек за PIN).
- Категория может нести способ отслеживания по умолчанию; позиция наследует его и может переключить.

### 4.2. Позиция (Item)

```
id, categoryId, name, unit (шт/таб/пак/кг/банка),
quantity (десятичное), minThreshold?, maxThreshold?,
expiresAt? (дата), packSize? («упаковка = N шт»),
trackExpiry (bool), trackQuantity (bool),
notes?, createdAt, updatedAt, updatedBy, deletedAt
```

**Режим отслеживания вкл/откл** — два независимых флага на позиции:
- хлеб (всё выкл) → просто списали и забыли;
- консервы (годность + остаток) → и срок, и «купить когда кончится»;
- пластыри (только остаток) → срок неважен.

**Семантика порогов:**
- `quantity <= minThreshold` → статус «🔵 пора купить»
- `quantity >= maxThreshold` → статус «🟣 избыток»

### 4.3. Статусы позиции (вычисляемые)

| Статус | Условие |
|---|---|
| 🔴 Просрочено | `expiresAt < сегодня` (при включённом `trackExpiry`) |
| 🟠 Истекает | `expiresAt <= сегодня + N дней` (N — глобальная настройка админа) |
| 🔵 Пора купить | `quantity <= minThreshold` (при включённом `trackQuantity`) |
| 🟣 Избыток | `quantity >= maxThreshold` |
| ⚪ В норме | остальное |

Приоритет при «сцепке» статусов: 🔴 > 🟠 > 🔵 > 🟣 > ⚪.

### 4.4. Журнал операций (ops)

Каждое действие: `type` (add/spend/restock/edit/delete/import-conflict), `delta` (изменение количества), `deviceLabel` (подпись устройства: «Папин iPhone»), `when`, `note` («унесли на дачу»), `itemId`, `deviceSeq`.

Назначение: «кто потратил последнюю банку», разбор споров, основа дельт для будущего сервера, отметки конфликтов импорта.

## 5. Экраны и UX

Таб-бар: **Дашборд · Треки · Добавить · Списать · Ещё**.

### 5.1. Дашборд (главная)
- Карточки-статусы с количеством позиций: 🔴 просрочено · 🟠 истекает через N дней · 🔵 пора купить · 🟣 избыток.
- Список «Срочное», сортировка: 🔴 → 🟠 → 🔵 → 🟣.
- Бейдж с общим числом проблем на иконке приложения (installed PWA).

### 5.2. Треки
Список треков (иконка/эмодзи, имя) + счётчик проблемных позиций у каждого.

### 5.3. Экран трека
Подкатегории → позиции, у каждой цветной кружок статуса. Сортировка по срочности внутри категории.
**Списывание в 1 тап:** тап по позиции → модалка «Списать: 1 / упаковка / своё число».

### 5.4. Списание (большой экран, из дашборда)
- Вверху «Недавние» (позиции, которые списывали чаще всего).
- Выбор позиции → количество (быстрые кнопки: 1, упаковка, своё) → примечание → «Списать».

### 5.5. Добавление (пачка)
Одна строка = одна позиция:

```
Название      ← автодополнение из «своих товаров» (история по имени)
Количество → Единица (шт/таб/пак/кг/банка)
Срок: [+1 мес] [+1 год] [своя дата] [не задан]
Категория     ← по умолчанию последняя использованная
Режим         ← наследуется из способа категории, переключаемо
```

Enter → следующая строка. Кнопка «Добавить N позиций».

### 5.6. Админ (в «Ещё», за PIN)
Способы отслеживания (CRUD), окно предупреждения N дней, название дома, подпись устройства, смена PIN.

### 5.7. Журнал
Лента операций, фильтр по треку/позиции: кто, что, сколько, когда, примечание. Конфликты импорта — с пометкой.

### 5.8. Экспорт / Импорт (в «Ещё»)
Три выгрузки — см. секцию 6.

## 6. Синхронизация, обмен, выгрузки

### 6.1. `дом-бэкап.json` — состояние всего дома
Весь дом: треки, категории, позиции, способы отслеживания, журнал, версия формата, мета (deviceLabel, exportedAt).

**Импорт = слияние, не замена:**
- каждая запись `{ id, updatedAt, updatedBy, deletedAt }` → LWW по `updatedAt`: побеждает та, чья метка новее;
- конфликт (эвристика): локальная запись изменена позже `exportedAt` файла **и** отличается от пришедшей → фиксируется в журнале; победитель тот же, по `updatedAt` (обычно локальная);
- могилки в файле удаляют локальные записи;
- журнал объединяется append-only, дубликаты по `deviceSeq` отбрасываются;
- сводка «файл принесёт N записей, M изменений, K конфликтов» показывается в предпросмотре до подтверждения импорта.

Это и есть синк в MVP: «Экспорт → поделиться (AirDrop/мессенджер/iCloud Drive) → импорт на устройстве супруги». Обе стороны теряют данные только при одновременном редактировании одной и той же позиции — редкий случай, фиксируется.

### 6.2. `состав-трека.json` — шаблон «такая же аптечка»
Подкатегории + позиции с нормативными количествами и единицами. **Без журнала, без персональных сроков** (сроки при импорте не переносятся — приёмник ставит свои).

Импорт = создание нового трека «Аптечка (копия)» со стартовыми количествами из шаблона.

### 6.3. `трек.pdf` — отчёт
Таблица «категория · позиция · кол-во · срок · статус», сортировка по срочности, шапка (имя трека, дата выгрузки, устройство). Для печати и отправки в мессенджеры.

### 6.4. Будущий серверный слой (вне MVP)
Supabase-подобный бэкенд + room-код дома (без регистрации). Меняет ТОЛЬКО транспорт: те же дельты/merge, что уже работают для файлов. Push-напоминания и 3-way merge появятся здесь. Роли начнут проверяться централизованно.

## 7. Обработка ошибок и защита

- **Импорт битого/чужого файла:** валидация версии формата и обязательных полей; **предпросмотр** «файл принесёт N позиций, M изменений» перед подтверждением; кнопка «Отменить».
- **Офлайн:** всё локально, сервер не нужен; приложение работает в авиарежиме.
- **PIN администратора:** хэш через WebCrypto (scrypt/PBKDF2), PIN не хранится в открытом виде, вводится для входа в настройки.
- **Данные семьи не покидают устройство иначе, чем явным экспортом пользователя.**

## 8. Тестирование

- **Unit:** merge-движок (LWW, могилки, дубликаты `deviceSeq`), вычисление статусов, сортировка.
- **Component:** экраны (дашборд, пачка-добавление, списание, импорт с предпросмотром).
- **Round-trip:** экспорт → очистка БД → импорт = состояние без потерь и без дубликатов журнала.
- **PWA:** установка на домашний экран, офлайн (Lighthouse PWA ≥ 90), touch-target ≥ 48px.

---

## 9. Критерии успеха MVP

1. Семья из 2+ iPhone ведёт общую аптечку и бакалею через обмен файлом-состоянием.
2. Списание ≤ 2 тапов; добавление пачки из 10 позиций ≤ 2 минут.
3. Импорт/экспорт никогда не теряет данные при конфликтах (merge + журнал).
4. Чужая семья импортирует «такую же аптечку» одним файлом-шаблоном.
5. PDF-отчёт пригоден для печати и отправки в мессенджер.
6. Устанавливается на домашний экран iPhone, работает офлайн.
