# Дизайн v2: CRM-каталог «Типы + Места» + настраиваемые единицы

- **Дата:** 2026-09-21
- **Статус:** черновик на ревью
- **Репозиторий:** `family-stock-tracker`
- **Основание:** дизайн от 2026-09-19 (`2026-09-19-tracker-design.md`), разделы 3.3, 4.1–4.2 и 6 обновляются этой спекой

---

## 1. Резюме

Пользователь подтвердил модель **A** («категория = тип позиции + способ отслеживания», админ ведёт глобальный каталог типов) и подход **«Типы + Места»**: бывшие `categories` переименовываются в `places` (места внутри треков, создаёт любой участник), добавляется глобальная таблица `types` (типы позиций, создаёт только админ, каждая ссылается на способ отслеживания), позиция получает `typeId` + `placeId`, добавляется таблица `units` (настраиваемые единицы вместо зашитого `UNITS`), а поля `minThreshold`/`maxThreshold`, скрытые в текущем UI, выводятся на экран добавления.

Схема данных сразу проектируется под будущий серверный синк (вариант 3 — гибрид): все новые записи наследуют `SyncFields` (`id/updatedAt/updatedBy/deletedAt`), LWW-слияние и могилки работают как уже описано в дизайне 2026-09-19 (раздел 3.2). В MVP синхронизация остаётся файловой (экспорт/импорт бэкапа со слиянием).

## 3. Модель данных v2

### 3.1. Сводная иерархия

```
ДОМ (семья)
 ├─ УСТРОЙСТВО: АДМИНИСТРАТОР / УЧАСТНИК        (+ PIN у админа)
 ├─ СПОСОБ ОТСЛЕЖИВАНИЯ (создаёт админ)         ← уже есть
 ├─ ТИП ПОЗИЦИИ (создаёт админ)                 ← НОВОЕ
 │    «Лекарства → срок+остаток» · «Консервы → срок» · «Крупы → остаток»
 ├─ ЕДИНИЦА (создаёт админ)                     ← НОВОЕ
 │    «шт, таб, пак, кг, г, банка, мл, л» и др.
 └─ ТРЕК (создают все)
      └─ МЕСТО (создают все)                    ← было «category»
           └─ ПОЗИЦИЯ (typeId + placeId)
                количество · единица · min/max · срок · режимы
```

### 3.2. Таблицы Dexie

| Таблица | Содержимое | Изменение |
|---|---|---|
| `household` | Дом, настройки | без изменений |
| `deviceProfile` | «Кто я на устройстве» | без изменений |
| `tracks` | Треки | без изменений |
| `places` | Места (бывш. `categories`): `trackId`, `name`, `emoji`, `sortOrder` | **переименование таблицы + поля** |
| `types` | Типы позиций: `name`, `emoji`, `trackingMethodId`, `sortOrder` | **новая таблица** |
| `units` | Единицы: `name`, `sortOrder` | **новая таблица** |
| `items` | Позиции: `placeId` вместо `categoryId`, новый `typeId` | **поле-переименование + новое поле** |
| `trackingMethods` | Способы отслеживания | без изменений |
| `ops` | Журнал операций | без изменений |

### 3.3. Типы

```ts
export interface Type extends SyncFields {
  name: string;            // «Лекарства»
  emoji: string;
  trackingMethodId: string; // способ отслеживания (срок/остаток)
  sortOrder: number;
}
```

- Глобальный каталог дома, **не привязан** к треку.
- **CRUD — только админ** (экран настроек за PIN).
- Удаление — мягкое (`deletedAt`), как у остальных записей.

### 3.4. Места

```ts
export interface Place extends SyncFields {
  trackId: string;         // ← как было у Category
  name: string;            // «аптечка дома»
  emoji: string;
  sortOrder: number;
}
```

- **Создают все** (админ и участник).
- Поля `trackingMethodId` у места **больше нет** — способ живёт в типе позиции.

### 3.5. Позиция

```ts
export interface Item extends SyncFields {
  placeId: string;         // ← было categoryId
  typeId: string;          // ← новое
  name: string;
  unit: string;            // строка из каталога units
  quantity: number;
  minThreshold: number | null;  // теперь редактируется в UI
  maxThreshold: number | null;  // теперь редактируется в UI
  expiresAt: string | null;
  packSize: number | null;
  trackExpiry: boolean;    // наследуется от типа при добавлении, переключаемо
  trackQuantity: boolean;  // наследуется от типа при добавлении, переключаемо
  notes: string;
  createdAt: number;
}
```

- Вычислимые статусы и их приоритет **не меняются** (спека 2026-09-19, раздел 4.3). Пороги min/max просто начинают заполняться из UI.

### 3.6. Единицы

```ts
export interface Unit extends SyncFields {
  name: string;            // «шт», «таб», «пак», «кг»…
  sortOrder: number;
}
```

- Каталог дома, **CRUD — только админ**.
- Позиция хранит `unit` строкой (как сейчас). Селект и отображение читают каталог; при отсутствии совпадения — фолбэк `'шт'`.
- Стартовое наполнение (сид) при создании дома: `шт, таб, пак, кг, г, банка, мл, л` с `sortOrder` по порядку.

## 4. Миграция

### 4.1. База (IndexedDB): схема v1 → v2

Dexie: `db.version(2).stores({...}).upgrade(tx => {...})`:

1. **`categories` → `places`**: переименовать таблицу, скопировать записи, **исключив** поле `trackingMethodId` (оно больше не используется местами; способ переезжает в типы).
2. **Создать `types`** из уникальных имён бывших категорий:
   - для каждой категории-исходника: если типа с таким именем ещё нет — создать `{ name: категория.name, emoji: категория.emoji, trackingMethodId: категория.trackingMethodId ?? СИД-дефолт, sortOrder }`;
   - **СИД-дефолт** = способ «Срок годности»; если у категории способа нет, а способа «Срок годности» в `trackingMethods` тоже нет — создать его (флаг `expiry: true`) и использовать;
   - позиции исходной категории получают `typeId` этого типа и `placeId` = id категории.
3. **Наполнить `units`** стартовым сидом, если пусто.
4. **`items`**: `categoryId` → `placeId` (то же значение), добавить `typeId` (по маппингу шага 2).

Идемпотентность: миграция выполняется один раз при переходе на схему v2; повторное открытие базы уже на v2 не триггерит upgrade.

### 4.2. Файл-бэкап: формат v1 → v2

`HouseholdEnvelope.version` поднимается до `2`; состав: `household, trackingMethods, tracks, types, units, places, items, ops`.

- **Импорт v1**: разворачивается в модельный v2 той же логикой, что и миграция базы (категории → места + типы + typeId; единицы сидом), затем идёт стандартное LWW-слияние. Старые бэкапы остаются читаемыми.
- **Экспорт**: всегда пишет v2.
- `ImportSummary` не меняется.

### 4.3. Шаблон трека (состав)

`TrackTemplateEnvelope.version` → `2`, поля `categories` → `places`, `TemplateItem.categoryId` → `placeName` (имя места) + новое `typeName` (имя типа).

- Импорт: места создаются заново в треке; типы ищутся по имени в каталоге дома, отсутствующие — создаются с СИД-дефолтом (способ «Срок годности», см. 4.1).

## 5. Экраны и UX (изменения против v1)

### 5.1. Экран трека
- Группировка позиций по **местам** (бывшая группировка по категориям).
- Кнопка **«+ Место»** на экране трека (видна всем — админ и участники): пустая строка с именем и эмодзи.
- Списывание «−1» и модалка списания — без изменений.

### 5.2. Админка (в «Ещё», за PIN)
Добавляются две секции к существующей «Способы отслеживания»:

- **«Типы позиций»**: список (имя, эмодзи, выбранный способ), **добавить/удалить**; способ выбирается при создании, затем не меняется (как у способов отслеживания в v1).
- **«Единицы»**: список, **добавить/удалить**.

### 5.3. Экран добавления
- Порядок выбора: **Трек → Место → Тип**.
- От типа наследуется способ отслеживания (флаги `trackExpiry/trackQuantity` в строке), единица по умолчанию — первая из каталога `units`.
- Появляются поля **min** («купить, когда ≤ N») и **max** («избыток, когда ≥ N») на строке добавления.
- Мульти-строки, автодополнение, кнопки «+1 мес / +1 год», Enter → следующая строка — без изменений.

### 5.4. Селекты единиц
- Везде, где единица выбирается/показывается (добавление, списание, трек, PDF), источник — каталог `units` из базы, а не константа `UNITS`.
- Константа `UNITS` удаляется из кода (или остаётся только как название сида).

## 6. Обработка ошибок и защита

- Импорт битого/чужого файла: как в v1 (валидация версии, предпросмотр, «Отменить»).
- Типы/единицы — мягкое удаление; каталог дома не теряет историю.
- Данные семьи не покидают устройство иначе, чем явным экспортом.

## 7. Тестирование

- **Unit:** миграция v1→v2 (категории→места+типы+typeId), конвертация бэкапа v1→модель v2, CRUD типов/мест/единиц и их права (админ/участник).
- **Component:** «+ Место» на экране трека, секции «Типы позиций» и «Единицы» в админке, селекты Трек→Место→Тип и единицы на добавлении, min/max влияют на статусы 🔵/🟣.
- **Round-trip:** экспорт v2 → очистка БД → импорт v2 = состояние без потерь; старый бэкап v1 импортируется корректно; шаблон трека v2 создаёт «такую же аптечку».
- **Полный прогон:** `vitest run`, `tsc --noEmit`, docker rebuild, проверка в Playwright.

---

## 8. Критерии успеха изменения

1. Админ создаёт типы («Лекарства → срок+остаток») и единицы; участник не видит этих секций.
2. Любой участник добавляет место в трек кнопкой «+ Место».
3. Новая позиция добавляется с выбором Трек → Место → Тип; min/max редактируются и влияют на статусы.
4. Старый бэкап v1 и старая база импортируются/мигрируются без потерь.
5. Полный прогон: vitest зелёный, tsc чистый, docker-сборка работает.
